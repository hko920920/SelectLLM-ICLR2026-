# PRAA source-fidelity amendment A

Date: 2026-08-14 (Asia/Seoul)

## Classification

This is an outcome-free source-fidelity correction. It is fixed before any
PRAA primary/deployment label, selector trajectory, regret, terminal choice, or
deployment metric is opened or computed.

The initial PRAA decision document correctly froze literal exact-match
acquisition/evidence, pool size, budget, temperature, paired runs, and fixed
query mediation. However, two implementation details were described too
generically:

1. it described primary root utility using the complete outcome block rather
   than the run-local sampled evaluation pool used by the source-faithful
   Step-93/113 implementation;
2. it described a fixed digest tie rule rather than the exact seeded stable-u64
   query/root tie rules used by Step 93.

No PRAA scientific outcome has been inspected. This amendment replaces those
phrases with the exact prior implementation semantics below.

## Exact pool sampling

For each frozen integer seed, sample without replacement using Python
`random.Random(seed).sample(range(N), min(500, N))`, then sort the sampled
indices in ascending order. Clean, refined, fixed-query, and root-aware
conditions share the identical pool matrix.

## Exact entry and root representation

For each task, the four canonical clean entries use the Stage-0 frozen registry
order and root indices `0,1,2,3`. The four derived entries append after the
clean entries and all map to the Stage-2 selected parent's clean root index.

The `core_codes` matrix is always the four clean root responses. It is used to
compute root utility; derived endpoint responses never redefine oracle root
quality.

## Exact same-s feedback and acquisition

For candidate code matrix `codes` and reference vector `references`:

- feedback is `1[codes == reference]`;
- at each item, entries are partitioned by literal response-code equality;
- with entry posterior `p`, acquisition is the sum over response groups of the
  squared group posterior mass;
- the active policy queries the unlabelled item minimizing this acquisition
  score.

After each acquired reference, every entry's accumulated exact-match score is
updated. The posterior is softmax of accumulated scores divided by frozen
`tau=0.05`.

## Exact run-local regret

For each run, root quality is the mean exact-match correctness of each of the
four clean roots **on that run's frozen sampled pool**. Let the best quality be
the maximum among those four values. The regret at a step is best pool quality
minus the selected root's pool quality.

- terminal regret is the final-step regret;
- cumulative regret is the sum through budget two.

This is the source-faithful estimand used by the prior confirmatory chain. Full
primary-block accuracy remains a descriptive task statistic, not the primary
run-level regret definition. The untouched deployment block remains the
separate prespecified practical endpoint.

## Exact tie rules

If multiple acquisition positions attain the same minimum, choose the position
minimizing:

`(stable_u64("step93", "query", seed, step, global_item_index), global_item_index)`.

If multiple entries attain the same maximum accumulated score, map them to
unique root indices and choose the root minimizing:

`(stable_u64("step93", "root", seed, step, root_index), root_index)`.

The exact `stable_u64` function is the first eight bytes of SHA-256 over the
pipe-separated string representation of its arguments, interpreted as a
big-endian unsigned integer.

These rules are applied identically to clean, refined, and fixed-query runs.
They are not selected using task outcomes.

## Fixed-query mediation

The fixed-query refined condition uses the exact query matrix generated by the
entry-indexed clean run. It updates the refined entry scores on those labels and
uses the exact root tie rule above. Primary mediation requires clean and fixed
root histories to be identical and fixed terminal/cumulative differences to be
exactly zero.

## Root-aware remedy

The root-aware canonical policy supplies exactly the four canonical clean
responses, masses, parent map, and root ordering in both clean and refined
registries. Derived manifests are admitted for audit but not inserted into the
selector code matrix. Therefore `R-clean` and `R-refined` execute the same
source-faithful code and must be bitwise identical.
